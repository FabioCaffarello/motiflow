# Integração AppBuilder Visual Completa com Evolução Planejada

## Contexto e Herança do Plano Pai

Este plano é filho de `transformação_appbuilder_em_next.js_app_bc0254d0.plan.md` e implementa a **Fase 10.1 e 10.2 (Migração do AppBuilder)**.

**Ponto de partida**:

- ✅ Domain Layer implementado (AppConfig, FeatureConfig, ComponentConfig)
- ✅ Application Layer implementada (Use Cases, DTOs, Mappers)
- ✅ Server Actions implementados (updateApp, getApp)
- ✅ AppEditor básico criado (estrutura, hook useAppEditor)
- ✅ AppBuilder completo existe no design system
- ✅ Análise de requisitos completa (`ANALISE_APPBUILDER_VISUAL.md`)
- ✅ Processo de evolução do design system estabelecido

**Regras fundamentais**:

1. **TDD obrigatório**: Escrever testes antes de implementar cada funcionalidade
2. **Evolução planejada**: Nenhum componente criado/evoluído sem análise rigorosa e plano filho
3. **Questionamento constante**: Sempre questionar se design system atende necessidades
4. **Documentação obrigatória**: Todas as decisões e análises devem ser documentadas

## Princípios de Evolução do Design System

### Quando Criar/Evoluir Componentes

**✅ Deve Criar/Evoluir**:

- Quando há limitação clara que impede desenvolvimento
- Quando há inconsistência que afeta UX
- Quando há oportunidade de simplificar uso
- Quando há necessidade de acessibilidade não atendida
- Quando composição não é suficiente

**❌ Não Deve Criar/Evoluir (Ainda)**:

- Por "ser mais moderno" sem necessidade real
- Por preferência pessoal sem justificativa técnica
- Quando pode ser resolvido com composição
- Quando impacto em outros projetos é muito alto
- Sem análise e planejamento rigoroso

### Processo Obrigatório

1. **Identificação**: Documentar em `improvements.md`
2. **Questionamento**: Responder checklist completo
3. **Análise**: Análise de impacto e alternativas
4. **Planejamento**: Criar plano filho detalhado (se necessário)
5. **Aprovação**: Revisar e aprovar antes de implementar
6. **Implementação**: Seguir TDD rigorosamente
7. **Validação**: Validar critérios de sucesso
8. **Documentação**: Atualizar documentação completa

- Design System permite `description?: string`
- **Ação**: Normalizar null para undefined durante mapeamento

## Decisões Arquiteturais

2. **Tratamento de Erros**: Validar antes de mapear, lançar erros descritivos
3. **Compatibilidade**: Manter backward compatibility sempre que possível

### 2.2 Implementação da Integração Básica

**Arquivo**: `admin/app-builder/src/features/apps/presentation/components/AppEditor/AppEditor.tsx`

**Mudanças**:

1. Importar AppBuilder do design system
2. Importar AppConfigMapper
3. Mapear initialConfig para formato do design system
4. Renderizar AppBuilder ao invés de JSON
5. Configurar callbacks básicos

**Estrutura**:

```typescript
export function AppEditor({ appId, initialConfig }: AppEditorProps) {
  const { config, updateConfig, save, isPending, error } = useAppEditor(
    appId,
    initialConfig
  );
  
  // Mapear config do domain para design system
  const designSystemConfig = useMemo(
    () => AppConfigMapper.toDesignSystemConfig(config),
    [config]
  );
  
  const handleConfigChange = useCallback((newConfig: DesignSystemAppConfig) => {
    // Mapear de volta para domain
    const domainConfig = AppConfigMapper.toDomainConfig(newConfig);
    updateConfig(domainConfig);
  }, [updateConfig]);
  
  return (
    <div className="h-screen flex flex-col">
      <AppBuilderHeader />
      <AppBuilder
        initialAppConfig={designSystemConfig}
        onConfigChange={handleConfigChange}
        embedded={false}
      />
    </div>
  );
}
```

**Nota**: Se AppBuilder não tiver `onConfigChange`, seguir Fase 2.0 para evoluir AppBuilder primeiro.
